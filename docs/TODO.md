# Satvis Space Compute & Multi-Satellite Collaboration - TODO & Roadmap

## 1. Core Requirements Overview (核心需求全景)

用户需求核心聚焦于：**轨道构造**、**多星协同计算**、**拓扑稳定度**、**日照区 GPU 利用率最大化** 以及 **算力状态平滑活体迁移**。

- **轨道构造 (Constellation & Orbit Design)**：支持自定义 Walker Delta / Star 及太阳同步轨道（SSO）参数设计（$P$ 轨道面, $S$ 每面星数, $h$ 高度, $i$ 倾角, $F$ 相位因子），直观呈现全局与局部日照角（$\beta$）分布及年均无影区比例。
- **多星协同 (Multi-Satellite Collaboration)**：支持大模型/深度学习推理分布式管线划分（$S_1 \to S_2 \to \dots \to S_n$），各阶段分布式驻留在低轨卫星节点上，通过星间链路（ISL）实现协同推理与 KV-Cache 交互。
- **稳定性 (Topology Stability)**：
  - 同轨固定环链（Rigid Intra-plane Ring Links，极低距离波动 $CV \approx 0.001$）；
  - 异轨同槽平滑链路（Same-slot Inter-plane Links，规避跨接异动）；
  - 剔除 Walker Star 逆向缝合面（Drop Seam，消除相对高速擦肩而过的链路抖动）；
  - 同周期集群刚性几何约束（Solid Bonds），异周期自动标识漂移（Dashed Bonds）；
  - **多轨道（多壳层）稳定布局**：不同壳层之间不存在刚性静止解，稳定的可达上界是"周期性回归"——先用 J2 进动率匹配锁住轨道面，再用沿迹速率共振锁住相位回归周期。
  - **稳定集群（Stable Cluster）**：两条判据都是**等价关系**，所以轨道空间本身已经被划分好了，"找集群"是求商而不是搜索——没有 k、没有质心、没有距离。需要算法的只有容差（容差破坏传递性，集群因此**相互重叠**而非划分），两阶段都是精确解：按 Ω̇ 排序取极大窗口（区间图，O(N log N)）+ 扫描候选周期（每个周期直接**点名**能闭合它的子集）。
- **提高日照区 GPU 利用率 (Maximize GPU Utilization in Sunlit Zone)**：
  - 太空计算载荷依赖太阳翼供电，仅在光照区（`sunlit_on` / `sunlit_edge`）全功率运行，地影/背光区（`umbra` / `penumbra` / `sunlit_back`）断电停摆；
  - **被动掉电迁移 (Naive Reactive)**：掉电后才被动换星，导致管线频繁停摆（日照区 GPU 实际有效利用率仅 30%~45%）；
  - **预判式协同交接 (Predictive Pre-Handoff)**：结合轨道几何与未来 90s 光照预判，在卫星进入地影前提前经 ISL 完成 KV-Cache 零中断换星交接，将**日照区 GPU 算力利用率提升至接近 100%（Zero Pipeline Stalls）**。
- **方便活体迁移 (Seamless Live Migration)**：
  - **地球不透明，穿地弦不是"长链路"而是"没有链路"**：通视是硬约束。`routesFrom` 在舰队可视图上跑 Dijkstra（按线长加权），交接走的是真实腿组成的最短路径——能直连就直连，否则绕过地平经由**有电中继**转发。跳数由几何决定而非预设：550 km 处一对卫星最多跨 42.5° 地心角，星球另一侧要五条腿，所以"单跳中继"是另一个错误答案。中继必须有电（背光星既不能收也不能发），可以同时是别的阶段的宿主；源端豁免（宿主正因即将进入地影才要交接）。没有任何有电链条绕得过去时，该阶段就是 `stranded`——这时它是事实而不是附注；
  - 目标星优选通视良好、剩余日照寿命最长且传输时延最短的空闲节点；
  - 状态全量持久化在 URL 参数中（`?mig=true&migst=4&migpol=predictive`），支持一键分享与无状态复现。

- [x] **交接距离与停留时间的量化 (How far does a hand-off reach, and how long does it hold?)**:
  - `scripts/research/migration-reach.ts`：用同一套 SGP4 + ν/κ 光照通道实测"宿主掉电瞬间，最近的有电卫星在多远"，并按**对目标剩余日照时长的要求**扫描，结论写在 `docs/migration-reach.md`；
  - **距离不由日影比例决定，而由"要求目标还能亮多久"决定**：53°/550 km 下 0 s→1274 km（单跳，从不 stranded）、600 s→3467 km、1800 s→7979 km（超出 5053 km 链路地平，必须两段中继）。全部构型在零要求下都落在 428–1428 km，即"一个格点"；
  - **朴素策略是一条链而不是一次交接**：目标中位数 140 s 后自己也掉电，20% 在 60 s 内掉电（暗弧约 2640 s）；预判 90 s 反而更近（988 vs 1279 km）——终点线附近的邻居正是和你一起掉电的那些；
  - **交接对象不是邻居**：零要求下目标的中位 Δplane = 4（共 10 面），约 0.4 P，即 RAAN 差 ~140° 的轨道面——轨道面相交使它几何上很近，而 RAAN 差得远使它的 β 和日照相位与你去相关；
  - **倾角是杠杆**：97.6° 下 506 km / 2 跳，87.9° Delta 下无论要求 0 s 还是 1800 s 都是 521 km（曲线是平的）；53° 下同样的要求要 7979 km 和两段中继。与 `orbital-compute.md` 的能量层结论同向；
  - **密度买不到停留时间**：N 翻倍只把零要求距离从 ~1400 压到 ~980 km，600 s 那一列在整个密度扫描里几乎不动（3255–4716 km）。
- [x] **同轨道交接 vs 最近交接，以及全舰队迁移的带宽账 (Ring hand-off vs nearest, and the fleet-wide bill)**:
  - **环内距离和停留时间是同一个量**：同一轨道面共享 β 和晨昏线，往后第 k 个槽既是 `2r·sin(kπ/S)` 远，也正好晚 `k·T/S` 秒进影。550 km / S=22 下每槽 261 s，直连最多够到 **k=2**（3904 km ≤ 5053 km 地平）= 522 s；实测 3906 km / 520 s，闭式与实测对上；
  - **同轨道交接更远但更便宜**：53°/550/10×22 下 —— 最近有电 1279 km / **格点 5 跳** / 停留 140 s；同面下一个亮槽 1973 km / **1 跳** / 260 s；同面视线内最远槽 3906 km / **2 跳** / **520 s**。距离贵 3 倍，跳数便宜 5 倍，停留多 4 倍。**贵的从来不是公里数，是跳数**；
  - **"多跳几个槽"正是要点**：只跳下一个亮槽买到的是最小停留（261 s 后再跳），是个跑步机；跳到地平允许的最远槽是把同一次交接做一次而不是 k 次——**每工作负载每圈迁移次数从 32.2 降到 9.2（3.5 倍）**；
  - **地平给出迁移率下界**：单跳能买到的停留不超过链路地平张的弧。350/550/1200 km 分别是 504/682/1154 s，即每圈至少 **10.9 / 8.4 / 5.7** 次。550 km 实测全部 ring-far 链条落在 7.6–9.5 次——这是地板不是策略，**只有高度能降低它**；
  - **环内代价是构型常数**：1971–1974 km / 260 s，在测过的每个倾角和两种 RAAN 张角下都一样（只取决于 S 和 h）。其他规则的数字都随倾角、β 和日期变，这一条不变；
  - **带宽根本不是瓶颈**：最忙的策略也只占单星一条 ISL 的 **0.21%**（97.6° naive nearest，每圈 73.9 次 / 148 GB），环策略在 0.02–0.05%。要到 10% 占空比，KV 得涨约 **100 倍**（~200 GB）或链路降到 ~1 Gbps。朴素策略真正的代价不是 bit，是每圈 32 次一致性风险窗口；
  - **也没有汇聚热点**：全舰队每 5 s 只有 1.0–1.5 颗（共 220 颗）进影，最忙的接收方同时只被 **1** 颗选中（某个构型 2 颗）。`migration.ts` 的无争用假设在这个规模上是准确的，不是简化；
  - **反应式策略的停摆时长 = 迁移次数 × 决策周期**，与轨道无关：20 s 采样下读作 3.4–4.6%，按 app 的 `MIGRATION_EVAL_SIM_SECONDS`（5 s）读作 0.8–2.8%。引用前必须说明周期；
  - **"等日出"永远不划算**：宿主重见阳光的中位时间在**每个倾角下都是 ~2640 s**（p10 2260–2580 s），没有哪个纬度能短暂入影后很快出来；
  - **高纬度那颗最近但不一定好**：入影集中在轨道转折纬度（53°→|lat| 43°，97.6°→80°），高倾角下轨道面在那里汇聚，所以最近有电星从 1279 km 降到 **506 km**——但它的剩余日照只有 **80 s**（全部规则里最差），因为它正因为同样的原因即将入影。例外是 87.9° Delta：521 km 且停留 3020 s。
- [x] **驻留时间才是被购买的量，以及"跳到刚进阳区的那颗" (Residence is what a hand-off buys)**:
  - 先把两个弧本身测出来（只统计内部完整段）：53°/550 km 下**日照弧 p50 3080 s**（p10 3060 / p90 3160，跨面只差 100 s）、**地影弧 p50 2660 s**、周期 5739 s。日照弧在全舰队几乎一致，所以天花板处处相同；
  - 由此得到**迁移次数的理论下界 = 周期 / 日照弧 = 1.86 次/圈**——永远落在某颗刚进阳区的星上。之前所有策略（naive 32.2、ring-far 9.2）都是这个下界的倍数，倍数就是浪费；
  - 新增 `fresh` 规则（选剩余日照最长的可达目标，允许中继）：目标 19918 km / **5 段** / 停留 **3020 s**（日照弧 3080 s，几乎拿满）；跟踪成链后 **1.9 次/圈——下界达成**；
  - **带宽守恒，变的只是切法**：ring-far 每圈 18.4 GB / 9.2 段，fresh 每圈 19.4 GB / 9.5 段——几乎一样，但迁移**事件数差 5 倍**。原因还是地平：买到的驻留 ∝ 走过的轨道弧 ∝ 段数，所以 `次数 × 段数` 沿有效前沿不变，而单段最多张 42.8°（550 km），故 **段传输次数/圈 ≥ 360°/42.8° = 8.4**，实测各规则 7.6–10.0；
  - 所以**可选的不是带宽，而是把它切成 9 次单跳还是 2 次五跳**——后者更好，因为一次迁移是一个一致性窗口和一次停摆，不只是字节。naive-nearest 是唯一落在前沿之外的（32.2 段/圈，下界的 3.8 倍）：它走的距离最短，贵在花了距离却没买到驻留；
  - **高倾角直接打破这个下界**：97.6° 下最"新鲜"的日照星只有 **3212 km、单跳**（在另一个 β 相位不同的轨道面上，靠跳相位而不是跑弧长），naive+fresh = **1.9 次/圈 / 3.8 GB/圈 / 占空比 0.005%**——比同倾角的 naive-nearest 少 17 倍迁移、39 倍带宽，也比 53° 的前沿好 5 倍。**轨道面之间的 β 分散，是让交接"不花距离就买到驻留"的那个条件**；
  - 三条诚实边界：`fresh` 是 oracle（直接读传播出来的真实剩余日照，实装要预测，但光照是元素集和日期的闭式函数）；五段中继意味着五颗别的星各自要暂存 2 GB，内存和功耗没建模；反应式策略的停摆 = 迁移次数 × 决策周期。
- [x] **把结论收敛成一条式子：每段传输买到多少轨道弧 (Arc bought per leg is the whole metric)**:
  - 三个前提：①地影扇区在惯性空间里一圈内基本不动（太阳每天才走 1°），550 km + 天顶板下**光照扇区宽 193°**（半球 + 两端各约 5.7° 的 `sunlit_edge`）；②**同一轨道面内，角度就是时间**——往后 k 槽 = `2r·sin(kπ/S)` 的弦 = `k·T/S` 秒，不是相关量而是同一个量的两种单位；③**单段不能超过链路地平**，550 km 下 5053 km = **42.8° 轨道弧**；
  - 于是整个问题是一句话：卫星每圈把负载往前带 360°，负载就得每圈往回跳 360°。所以 `迁移次数/圈 = 360° / 每次买到的弧`，`段数/圈 = 360° / 每段买到的弧 ≥ 360°/42.8° = 8.4`。**两个分母互相独立**——前者是把 360° 切成几个事件，后者是切成几次传输，只有后者有下界；
  - **一段传输不管跨 1° 还是 42.8°，都要付一次完整的 KV 序列化（2 GB / 100 Gbps = 160 ms）**，所以策略的品质指标就是**每段买到的弧**（上限 42.8°）：naive-nearest **9°/段（21%）**、环内下一槽 16°（37%）、环内最远槽 33°（77%）、预判+环内最远 38°（89%）、最新鲜日照 38–39°（89–91%）；
  - **naive-nearest 的问题不是走得远，恰恰是它走得最近**（1254 km，全部规则里最短）。它花了一整段传输只买到 9° 相位，因为它交给正后方那颗——那颗马上要过同一条晨昏线；
  - **真正的选择只剩"怎么切 360°"**：环内最远槽和最新鲜日照效率相同（~38°/段），所以搬的字节相同（18.4 vs 19.4 GB/圈），区别是 **9.2 次 × 1 段** 还是 **1.9 次 × 5 段**——带宽一样，事件数差 5 倍，停摆 0.8% vs 0.2%。KV 解码场景下一次迁移是一次停摆 + 一次丢状态的机会，所以"少而大"通常是对的那一边；代价是五个中继各要暂存 2 GB，这一项没建模；
  - **式子里 `360°/弧` 用的是均值而表里给的是中位数**：偏斜大的规则（naive-nearest）中位数低估，360°/9° 预测 40 次而实测 32.2；高效规则很紧，360°/38° = 9.5 对实测 9.2/9.3，360°/189° = 1.9 对实测 1.9；
  - **高倾角为什么能突破 8.4**：8.4 来自前提②，而②只在**单个轨道面内**成立。跨轨道面且 β 不同时，另一个面的光照扇区在不同的 φ 上，于是可以**换相位而不走弧长**——97.6° 下最新鲜日照星 3212 km 单跳，42.8° 的天花板根本不适用。
- [x] **从单个负载扩展到整个星座：容量、争用、以及"不用建调度器"这个否定结论 (One workload vs the whole constellation)**:
  - 前面所有链条都是**各自独立**跟踪的（两个负载可以选同一个目标而互不计费），这对"大舰队上一条管线"是对的模型，对"整个星座都在算"就是错的。新增 `measureCapacity`：每星一个负载、共同争用同一批有电星、目标必须**空闲且可达**；
  - **容量上界是硬的，不是分布**：53°/550 km 下同时有电的星是 **117–120 / 220**（均值 54.0%，只抖 ±1.3%）。所以**定容量就是一次除法**：要跑 W 个负载就要 `W / 日照比例` 颗星。倾角直接抬这个比例——97.6° 是 122–125（56.1%），同样 220 颗能多装 4 个负载；
  - **贪心局部规则就能把舰队跑到这个上界**：满载（W=118，恰好等于有电星数）时各规则 98.5–99.8%，最好的和理论最优只差零点几个百分点，规则之间只差 1.3 个百分点。争用从来没成为约束——每 5 s 全舰队只有 1.2 颗过晨昏线，而每颗都有半个天球的候选；
  - **这是一个值得拥有的否定结论**：没有全局分配问题、没有匹配、没有调度器能买到东西。**全部可得的收益都在迁移代价上**（每段买到的弧），不在布站上。工程量该投到那边；
  - **过载则一律崩到算术极限**：load 1.10（W=130 > 119）时所有规则都是 91–93%，正好是 119/131。策略在上界之外完全不起作用；
  - **满载下的最优行是**：naive-nearest 99.8% / 32.2 次，环内最远槽 98.5% / 9.2 次，**预判 90 s + 最新鲜日照 99.5% / 2.0 次**——用 0.3 个百分点的服务时间换 **16 倍更少的迁移事件**；
  - **短环的日照星数抖动最大**（20×11 是 116–122，对比 5×44 的 118–121），满载服务也最差（96.8–98.8%）——长环把有电星数抹平了，这是 S 的一个此前没注意到的作用；
  - 未建模：一星一负载、迁移对占用视为瞬时、负载按固定顺序处理（贪心启发式而非最优——但结论正是"贪心就够了"）、中继暂存 2 GB 的内存与功耗。
